# Kiro 企业研发实战 Workshop

## 学员手册

### 场景

我们将为一个虚构的网约车平台设计“取消订单与爽约费规则中心”。业务团队希望统一各城市的收费逻辑，兼顾乘客体验和司机权益，并支持运营配置、客服解释、异常降级和审计。

原始需求中有许多团队日常工作里常见的表达：

- 前几分钟可以免费取消；
- 司机已经很接近上车点；
- 等待一段合理时间后可以判定爽约；
- 恶劣天气可以提高费用，也要适当照顾乘客；
- 系统应该尽快返回结果。

Workshop 的任务不是猜出这些话“应该是什么意思”，而是把它们转成团队可以共同确认、实现和验证的规则。

## 我们的工作路径

```text
理解上下文
→ 发现需求问题
→ 确认业务决策
→ 创建 Feature Spec
→ 评审设计和任务
→ 查找并复用企业已有资产
→ 建立团队规则
→ 实现与测试
→ 修复缺陷
→ 审查和复盘
```

## 需求分析时关注什么

### 歧义

是否出现“尽快”“合理”“比较远”“适当”等无法直接实现的表达？

### 冲突

两条规则是否可能同时命中，却给出不同结果？

### 缺失

是否缺少范围、边界、优先级、异常行为、权限或审计要求？

### 可验收性

产品、开发和测试能否对“完成”得出相同判断？

### 决策归属

这个问题应该由产品、架构、开发、测试、安全、法务还是运营回答？

## Spec 评审时关注什么

### Requirements

- 是否使用明确、可判断的条件和结果；
- 是否覆盖边界值和异常；
- 是否能追溯到原始需求或已确认决策；
- 是否把待确认内容误写成确定规则。

### Design

- 领域规则是否与地图、支付等外部系统隔离；
- 金额、时间、规则版本和证据是否有清晰模型；
- 幂等、降级、审计和权限是否进入设计；
- 是否为一个教学目标过度设计整套平台。

### Tasks

- 每项任务是否足够小，可以独立审查；
- 是否标明关联 Requirement；
- 是否有明确的验证方式；
- 是否夹带无关重构。

## 本次使用的核心业务不变量

```text
0 <= 乘客取消费 <= 订单预估完单价格
```

同时要求：

- 安全、法律、无障碍或关键系统异常时，乘客费用为 0；
- 同一订单和收费类型最多产生一笔成功扣款；
- 相同输入证据和规则版本应得到相同判定；
- 关键依赖异常时，订单仍可取消，恢复后不追扣乘客。

## 容易混淆的 Kiro 概念

| 概念 | 主要作用 |
|---|---|
| Skills | 按需加载特定知识、工作流和模板 |
| Steering | 提供项目长期遵守的上下文规则 |
| Custom Agents | 封装专业角色、上下文、工具和权限 |
| Supervised | 每轮修改由人逐段审查 |
| Autopilot | 在明确任务和护栏下连续执行 |
| Permissions | 控制 Agent 可以调用的工具和路径 |
| `.kiroignore` | 排除不应进入上下文或索引的内容 |

## 现场可复用的提示词

### 先理解，不修改

```text
先不要修改文件。请说明当前已经确认的事实、你的推断和仍需业务确认的问题，并为每个结论引用来源。
```

### 分析需求

```text
请找出这份需求中的歧义、冲突、缺失和不可验收内容。每项引用原文，并给出一个需要业务负责人明确回答的问题。先不要替业务做决定。
```

### 查找企业已有费用组件

```text
/custom-find-skill 为已经判定需要收费的取消订单实现费用金额计算：应用运营调整和用户减免，结果不能为负且不能超过预估完单价格。请先查找团队已有的业务知识、公共组件和代码模板，不要重新实现费用算法。
```

检查输出是否包含真实路径、包级 API、模板、明确排除项和禁止重复实现项。

### 实施前确认范围

```text
在修改前，请说明将处理哪个 Requirement、修改哪些文件、明确不改什么，以及准备如何验证。
```

### 测试失败后分析根因

```text
先不要修复。请给出可复现输入、期望结果、实际结果、计算过程和根因证据，再提出最小修改方案。
```

### 审查 Diff

```text
请按业务行为评审这份 Diff：改变了什么、哪些行为保持不变、新测试是否能在旧实现上失败，以及是否包含无关修改。
```

## 小组讨论

1. 哪些问题可以由 Agent 推导，哪些必须由业务负责人决定？
2. 哪些约束适合写进 Steering，哪些必须由测试或权限强制？
3. 什么时候应该使用 Supervised，什么时候可以使用 Autopilot？
4. Property Test 通过后，还有哪些风险需要人工评审？
5. 开发会话、规则配置记录和订单账务记录有什么区别？

## 课后练习

选择一项继续完成：

- 为“司机 ETA 明显增加时免费取消”补齐需求和测试；
- 设计并验证并发重试下的收费幂等；
- 为普通客服和高级客服设计不同的数据视图；
- 为城市规则设计审批、灰度和回滚流程；
- 创建一个只读测试评审 Agent，并验证它不能修改代码。

本课程中的公司、订单、数据和参数均为教学示例。
