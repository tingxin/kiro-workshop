# Workshop 提示词库

## 使用规则

1. 先附加最小必要上下文，再发送 Prompt。
2. 文档分析阶段明确“不要修改文件、不要替业务做决定”。
3. 实施阶段明确允许修改的范围和验证命令。
4. 高风险动作使用 Supervised，并设置 Permissions。
5. Prompt 中的文件选择器请按现场 Kiro 版本使用，例如 `#File`、`#Folder`、`#Terminal`、`#Problems`、`#Git Diff`。

---

## P07：创建 Feature Spec

```text
为“取消订单与爽约费规则中心 V1”创建 Feature Spec。

上下文规则：
- 原始业务文档是需求来源。
- 模拟产品确认记录是本次 Workshop 的 V1 基线。
- 两者冲突时，以确认记录为准并记录差异。
- 未确认事项不得擅自实现。

Requirements：
- 使用 EARS 风格。
- 每条有唯一 Requirement ID。
- 包含验收条件、边界示例和来源追踪。
- 明确 V1 范围、规则优先级、时间/金额单位、爽约门控、费用封顶、幂等、降级、可解释性和审计。

Design：
- 聚焦纯领域规则引擎。
- 外部地图、支付、通知和风控通过端口与 fake 实现。
- 设计 Evidence Snapshot、Rule Version、Decision、Charge、Compensation 和 Audit Event。
- 可注入 Clock，金额使用整数分。

Tasks：
- 只覆盖最小纵切。
- 按依赖排序并保持任务可独立审查。
- 每项说明关联 Requirement ID、修改范围和验证命令。
- 不实现真实地图、支付、通知或生产部署。
```

## P09：Design 与 Tasks 评审

```text
评审当前 Spec 的 Design 和 Tasks，不修改文件。

请检查：
1. 领域逻辑是否与外部系统解耦；
2. 金额、时间、Clock 和 ruleVersion 是否有明确建模；
3. 幂等收费和审计是否有原子性边界；
4. 降级是否保证取消成功且乘客不收费；
5. 每个关键 Requirement 是否有实现任务和验证任务；
6. 是否存在过大、不可独立审查或无法验证的任务；
7. 是否意外扩展到真实地图、支付和生产基础设施。

给出最小修改建议，不要重写整个 Spec。
```

## P10：Spec Correctness/追踪分析

```text
检查当前 Spec 的 Requirements、Design、Tasks 和测试计划是否双向可追踪。

重点检查：
- 强免责是否能压过所有加价和用户风险规则
- 费用是否始终非负且不超过预估车费
- 爽约是否具备验证到达、等待和联系条件
- 降级是否可能在恢复后追扣乘客
- 幂等是否覆盖重试、乱序和并发
- 历史决策是否能由相同输入快照和 ruleVersion 重放

对每个缺口给出 Requirement ID、缺失环节、风险和最小修复建议。明确说明这是一致性与可追踪性分析，不是商业公平性或法律合规证明。
```
