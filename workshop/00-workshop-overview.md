# 从模糊需求到可靠交付

## Kiro 企业研发实战 Workshop

一家网约车平台准备统一“取消订单与爽约费”规则。产品团队给出了一份看似完整的需求：要兼顾乘客体验和司机权益，要支持不同城市灵活配置，也要处理天气、安全、系统异常和用户申诉。

真正开始研发时，团队很快会遇到问题。现场使用的原始材料是这份[取消订单与爽约费规则中心需求](../cancellation-no-show-fee-raw-requirements.md)：

- “前几分钟可以免费取消”，到底是几分钟？
- 司机“已经到达附近”，由谁判断，边界在哪里？
- 恶劣天气既要补偿司机，又要照顾乘客，两条规则谁优先？
- 规则中心不可用时，是沿用旧规则，还是先取消、后补算？
- 需求写了“同一订单只能收费一次”，并发重试时如何保证？

这次 Workshop 会从这份原始业务文档出发，现场完成一次接近真实团队协作的研发过程：澄清需求、形成设计、拆分任务、实现规则、发现缺陷、验证修复，并讨论企业环境下的权限和审计。

## 我们会一起完成什么

### 1. 先理解，不急着写代码

我们会通过 Agent Chat 为 Kiro 提供业务文档、现有工程和运行结果，让它梳理取消判定、费用计算、规则配置和审计之间的关系。重点不是让它快速给答案，而是看它能否区分：文档已经明确的事实、合理推断，以及必须由业务负责人确认的问题。

### 2. 把模糊需求变成可以讨论的决策

我们会使用 Analyze Requirements 从原始文档中找出歧义、冲突和不可验收的描述。产品、架构、开发和测试将从各自视角参与澄清，形成第一版范围和关键规则。

例如：

- 哪些订单进入第一版；
- 免费取消和乘客爽约的时间边界；
- 安全、无障碍和系统异常的免责优先级；
- 金额计算、封顶和减免的顺序；
- 重复请求、降级和历史重放的处理方式。

### 3. 用 Spec 连接需求、设计和任务

在业务决策确认后，我们会创建 Feature Spec，将讨论结果转成可审查的 Requirements、Design 和 Tasks。

这一过程会回答三个问题：

- 产品需求是否已经可以验收；
- 技术设计是否覆盖关键边界和异常；
- 每一项实现任务是否能够追溯到明确需求。

随后使用 Spec Correctness 检查 Requirements、Design、Tasks 和测试之间是否存在遗漏或断链。

### 4. 在写代码前发现企业已有资产

针对“取消费金额调整、减免与封顶”这一小段通用逻辑，我们会调用 `custom-find-skill`，查找企业已经确认的业务知识、`MoneyMinor`/`CappedFeeCalculator` 公共组件和费用集成模板。

这个环节只回答“公司已经有什么可以复用”，不负责完整取消判定，也不代替 Spec、Steering 或测试。

### 5. 把团队规范放进研发过程

我们会为项目建立 Steering，让 Kiro 持续遵守团队约定，例如金额使用整数分、时间统一使用 UTC、敏感信息不得进入日志、外部系统通过接口隔离。

随后通过 Agent Hooks 自动执行类型检查和目标测试，让规范不仅存在于文档中，也进入日常开发流程。

### 6. 在可控范围内让 Agent 完成开发

现场会对比 Supervised 和 Autopilot 两种协作方式：什么时候应该逐段审查，什么时候可以让 Agent 在明确任务和测试保护下连续执行。

我们还会演示 Permissions、`.kiroignore` 和 Custom Agents，说明企业团队如何限制工具能力、隔离敏感内容，并为需求分析、安全评审等角色配置不同的职责范围。

### 7. 用一个隔离注入的缺陷完成研发闭环

默认 Starter 不包含缺陷完成态。学员必须先完成费用纵切、运行测试并建立 `RP-07-implemented` 恢复点；随后讲师才在独立副本或可恢复 Checkpoint 中注入一个“调整后未最终封顶”的回归。

测试应给出一个清晰反例，但具体失败输出必须来自隔离故障状态，而不是伪装成默认仓库结果：

```text
基础取消费：8 元
预估完单价格：10 元
天气系数：2
错误结果：16 元
正确结果：10 元
```

学员让 Kiro 先诊断证据，再创建 Bugfix Spec、完成最小修改，并通过属性测试、目标测试和 Git Diff 验证。讲师不得把预制修复代码复制到学员工作区。

### 8. 回到企业真正关心的问题

最后，我们会讨论三类容易混淆的审计：

- 开发过程中，Agent 做过什么；
- 业务规则由谁创建、审批和发布；
- 某一笔订单为什么收费、补偿或退款。

Workshop 会以一次脱敏后的会话导出结束，展示如何把研发过程留作复盘材料。

## 课程安排

## 课程形式

本项目提供两条连续路线：

- **90 分钟核心 Workshop**：完成 Starter、需求分析、人工决策、Decision Log、Feature Spec、资产发现和费用纵切；目标是熟悉 Kiro 的端到端协作方式，不宣称完成原始需求全文。
- **多阶段完整 Lab**：继续执行 [动手实验手册](03-hands-on-lab-guide.md) 的 Lab 8–12，实现已批准 V1 Spec 中的取消判定、可靠性、客服/运营/审计参考能力、兼容模拟和最终验收。

核心 Workshop 参考安排：

| 环节 | 学员操作 | 参考时间 |
|---|---|---:|
| Starter | 检查默认工作区没有完成答案 | 5 分钟 |
| 需求分析 | 用 Kiro 生成有证据的阻塞问题 | 12 分钟 |
| 人工决策 | 角色讨论并由学员创建 Decision Log | 12 分钟 |
| Feature Spec | 学员创建并评审 Requirements、Design、Tasks | 18 分钟 |
| 验证设计 | 追踪矩阵和 Property 设计 | 8 分钟 |
| 企业资产复用 | `custom-find-skill` 查找知识、组件和模板 | 8 分钟 |
| 测试与实现 | Red→Supervised 实现→Green→Diff | 17 分钟 |
| 护栏与复盘 | Steering、Hook、恢复点和边界总结 | 10 分钟 |

完整参考系统必须使用多阶段 Lab；不能通过压缩讨论、复制讲师答案或预置完成代码来伪装完成。

## 适合谁参加

- 产品经理：学习如何把业务描述转成可决策、可验收的需求；
- 架构师：观察规则边界、降级、幂等和审计如何进入设计；
- 开发人员：体验从代码理解到实现、测试和 Diff 审查的完整过程；
- 测试人员：从业务不变量出发设计边界测试和属性测试。

## 你将带走什么

- 一套从原始需求到 Feature Spec 的分析方法；
- 一组可直接复用的 Kiro 提示词；
- Steering、Hooks、Permissions 和 Custom Agents 的项目实践；
- 一个包含故障、测试和修复过程的完整演示案例；
- 一份适合团队内部继续演练的 Workshop 工程。

本课程中的公司、订单、数据和业务参数均为教学示例。
